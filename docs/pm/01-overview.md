# 기획 문서 지도
어떤 상황에 어떤 문서를 쓰는지, 문서끼리 어떻게 이어지는지.

## 일의 흐름과 문서
```text
문제 발견 ─ 사용자 리서치, 지표 정의서
   ↓
문제 정의 ─ PRD
   ↓
우선순위 ─ 백로그·우선순위
   ↓
설계 ─ 기능 명세서, 유저 스토리·인수 조건
   ↓
나눠서 만들기 ─ 단계 분리·스프린트
   ↓
검증 ─ 실험 설계서, QA·출시 체크리스트
   ↓
공유와 회고 ─ 릴리즈 노트, 주간 보고, 회고, 의사결정 기록
```

## 채용 공고의 요구와 문서
PM·PO 공고에서 반복되는 요구를 문서에 대응시켰다.

| 공고의 요구                    | 보여주는 문서              |
|--------------------------------|----------------------------|
| 유저 보이스·데이터로 문제 발굴 | 사용자 리서치, 지표 정의서 |
| 가설 → 실험 → 분석 → 개선      | 실험 설계서, 회고          |
| 지표로 성과 증명               | 지표 정의서, 주간 보고     |
| 우선순위 결정                  | 백로그·우선순위            |
| 문제 발굴부터 출시까지 주도    | PRD, 단계 분리·스프린트    |
| 개발·디자인·운영과 협업        | 기능 명세서, 의사결정 기록 |

## 예시 과제
모든 문서의 예시는 같은 과제 하나로 이어진다.

- 과제: 알림 설정 개편
- 상황(가정): 알림이 많다고 느낀 사용자가 푸시를 통째로 끈다. 꼭 필요한 알림까지 못 받는다.
- 해결: 푸시 아래에 종류별 하위 설정을 두고 켜짐 방향을 통일한다. [토글](#/components/toggle)의 데모가 그 결과물이다.

예시의 수치는 문서 형식을 보이기 위한 가정 값이다. 실제 서비스의 결과가 아니다.

## 항목별 기획 문서
블록과 컴포넌트 상세에서 **기획** 보기로 바꾸면 그 항목의 기능 명세가 나온다. 블록은 PRD 요약을 함께 둔다.
