# PRD
무엇을 왜 만드는지 한 문서로 합의한다. 만드는 방법은 기능 명세서로 넘긴다.

## 언제 쓰나
- 2주 이상 걸리거나 여러 직군이 함께 하는 과제를 시작할 때
- "왜 이걸 하나"를 리더·개발·디자인에 같은 말로 설명해야 할 때

작은 개선은 한 장(문제·해결·지표)으로 줄인다. 템플릿의 모든 칸을 채우는 것이 목적이 아니다.

## 템플릿
```markdown
# <과제 이름>
작성자 · 상태(초안/합의/진행/완료) · 마지막 수정일

## 문제
- 누가, 어떤 상황에서, 무엇 때문에 곤란한가
- 근거: 데이터·VOC·리서치 (출처 링크)

## 목표
- 핵심 지표: <지표 이름> 현재 → 목표 (기간)
- 가드레일: 나빠지면 안 되는 지표

## 해결 방향
- 한 문단. 화면 시안·흐름도 링크

## 범위
- 이번에 한다
- 이번에 안 한다 (이유)

## 요구사항
- 기능 명세서 링크, 핵심 유저 스토리 3~5개

## 위험과 확인할 것
- 가정, 의존성(법무·운영·외부 API), 열린 질문

## 출시 계획
- 단계(내부 → 일부 사용자 → 전체), 실험 여부, 롤백 조건
```

## 예시: 알림 설정 개편
```markdown
# 알림 설정 개편
상태: 합의

## 문제
- 알림이 많다고 느낀 사용자가 푸시를 통째로 끈다. 댓글·거래처럼 꼭 필요한 알림까지 놓친다.
- 근거(가정): 설정 화면 진입 후 푸시를 끄는 비율이 높다. VOC에 "필요한 알림만 받고 싶다"가 반복된다.

## 목표
- 핵심 지표: 푸시 전체 끄기 비율 감소
- 가드레일: 알림 클릭률, 알림 관련 문의 수

## 해결 방향
- 푸시 아래 종류별 하위 설정(댓글·답글, 야간 알림)을 둔다.
- 모든 토글은 켜면 받는 방향으로 통일한다. "방해 금지" 같은 부정형 라벨을 없앤다.

## 범위
- 한다: 설정 화면 구조, 상하위 연동, 라벨 정리
- 안 한다: 알림 발송 빈도 조절(발송 정책 과제로 분리)

## 위험
- 하위 설정이 많아지면 오히려 복잡해진다 → 1차는 2개만
- 서버의 알림 설정 스키마 변경 필요 → 백엔드 일정 확인

## 출시 계획
- 10% 사용자 실험 → 지표 확인 후 전체
```
